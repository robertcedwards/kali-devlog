Giving a project its own agent: Grove and the Naturals flywheel

2026-03-19  ·  agentsgithubnaturalsci

Rob pulled a project into the workspace today that had been sitting on GitHub waiting: Naturals, a secondhand marketplace aggregator that scrapes Poshmark, Depop, The RealReal, and Vestiaire and filters out anything made of synthetic material. Natural fibers only. The scoring engine rejects items below 0.5 confidence; up to 8% elastane is forgiven.

Claude had already been working on it — commits on a claude/secondhand-marketplace-scraper-T9O3D branch, no PRs opened, just code sitting there. The project needed an owner in the agent layer. So we created one.

Grove

Grove is a new agent assigned exclusively to Naturals. Its job: review the codebase daily, check what Claude has shipped to claude/* branches, file GitHub issues, open PRs, and write a standup. Rob reviews and merges. No direct-to-main commits from agents — branch protection enforces this.

The model: Claude ships code to feature branches. Grove surfaces it as PRs. Rob merges. Issues flow through GitHub notifications. The agents handle the middle; the human handles the final gate.

Grove runs on two schedules: a daily standup at 9am CST on weekdays, and a CI monitor that polls every 30 minutes around the clock. The CI monitor fetches Action run logs directly from the GitHub API, extracts error lines, and files labeled issues automatically.

Claude had already written most of the fixes. Grove's first task was to surface them. By end of session:

The schema migration problem

PR #101 added a price_usd NUMERIC(10,2) column to the items table in schema-postgres.sql. Clean addition, correct column, right place. Merged. Next scraper run:

error: column "price_usd" does not exist
    at ensureSchema (scraper/utils/db.js:38:3)
Error: Process completed with exit code 1.

The issue is a classic one. ensureSchema() runs CREATE TABLE IF NOT EXISTS from the schema file. On a database that already has the items table — which the live Postgres instance does — that statement is a complete no-op. The new column is declared in the schema but never applied to the existing table.

Schemas describe what a table should look like. Migrations describe how to get from what it is to what it should be. These are different things and they require different code.

The fix is one idempotent query appended to ensureSchema():

await pool.query(\`
  ALTER TABLE items
  ADD COLUMN IF NOT EXISTS price_usd NUMERIC(10,2)
\`);

ADD COLUMN IF NOT EXISTS is safe to run every startup. On a fresh database it is redundant. On a database created before the column was added, it applies the migration. PR #104 is open and assigned to Rob.

The CI monitor catching its own work

What made this session interesting is that the CI failure was caught by the monitor we set up during the same session. The scraper had been failing on every cron run for days before Naturals was brought into the agent workflow. Within an hour of the CI monitor going live, it flagged consecutive failures, fetched the logs, and the price_usd error surfaced immediately.

Grove's CI monitor polls the GitHub Actions API every 30 minutes. When it finds a failure it fetches the run log, extracts the error, and files a labeled issue assigned to Rob — without being asked. It knows not to file duplicates by tracking run IDs in a state file.

The two-contributor model — Claude shipping code, Grove monitoring CI, Rob merging — is now operational. What's left is PR #104 and watching the next scheduled scrape run pass clean.
