Langfuse Agent Tracking: Three Bugs, One Session

2026-03-05 — observability langfuse agents debugging infrastructure

The goal was simple: make each agent show up as a distinct user in Langfuse’s Users tab, with individual cost and token tracking. The docs say to pass a user_id field. We did that. Nothing appeared. Then we found three separate reasons why.

Protocol

Builder agent wrote the implementation. The design: an AGENT_USER_IDS dict in models.py mapping 13 identities (agent:floyd, agent:ops, agent:builder, etc.), a ContextVar named _langfuse_agent_user_id for async-safe storage, and two new extensions:

  • /a0/python/extensions/message_loop_start/_20_set_langfuse_user_id.py — reads the active project name, sets the ContextVar
  • /a0/python/extensions/util_model_call_before/_20_inject_langfuse_user_id.py — stamps utility calls

Every acompletion() call gets metadata: { trace_user_id: 'agent:builder', user_id: 'agent:builder' } injected. Commit 0a364db. Implementation looked correct. Nothing showed up in Langfuse. Time to debug.

Bug 1 — Agents not visible in Agent Zero UI

Agent Zero discovers projects by scanning PROJECTS_PARENT_DIR = 'usr/projects', which resolves to /a0/usr/projects/. Our ten agent profiles lived in /a0/usr/workdir/agent-zero-workspace/agents/. That directory is outside the scan path. Agent Zero never saw them. The project switcher was empty for everything we’d built that morning.

Fix: ten symlinks.

ln -s /a0/usr/workdir/agent-zero-workspace/agents/floyd /a0/usr/projects/floyd
ln -s /a0/usr/workdir/agent-zero-workspace/agents/ops /a0/usr/projects/ops
ln -s /a0/usr/workdir/agent-zero-workspace/agents/builder /a0/usr/projects/builder
# × 10

All ten agents appeared in the project switcher. No file moves, no duplication. Symlinks pointed the scan path at the actual source. This is the correct fix — the workspace stays canonical.

Bug 2 — langfuse SDK not installed in A0’s Python

The container runs two separate Python environments. The terminal uses /opt/venv (Python 3.13). The Agent Zero framework uses /opt/venv-a0 (Python 3.12). LiteLLM v1.79.3 lives in A0’s venv. langfuse did not. When LiteLLM tried to fire the success_callback, the SDK wasn’t there. It failed silently — no exception, no log line, no trace.

Fix: install in the correct environment.

/opt/venv-a0/bin/pip install langfuse
# Successfully installed langfuse-3.14.5

Two Python environments in one container is a thing that exists and will quietly waste an afternoon if you forget about it. The terminal telling you langfuse is installed means nothing when the framework runs a different interpreter.

Bug 3 — Import-time env check

This one was the interesting one. The original models.py configuration block:

_langfuse_configured = (
    os.environ.get("LANGFUSE_PUBLIC_KEY")
    and os.environ.get("LANGFUSE_SECRET_KEY")
    and os.environ.get("LANGFUSE_HOST")
)
if _langfuse_configured:
    litellm.success_callback = ["langfuse"]

This runs at module import time. The .env file is loaded in initialize.py — which imports models.py after its own setup. By the time Python evaluates that block, os.environ.get() returns None for all three keys. The callback never registers. Langfuse never receives anything. Everything downstream of this was a no-op.

Fix: replace the block with a lazy helper and call it inside unified_call():

def _ensure_langfuse_callback() -> bool:
    if os.environ.get("LANGFUSE_PUBLIC_KEY") and \
       os.environ.get("LANGFUSE_SECRET_KEY") and \
       os.environ.get("LANGFUSE_HOST"):
        if "langfuse" not in (litellm.success_callback or []):
            litellm.success_callback = ["langfuse"]
        return True
    return False

_ensure_langfuse_callback() is called at the top of unified_call(). By then, initialize.py has already loaded the .env. The env vars exist. The callback registers. Commit 2b879de.

Results

After all three fixes, we verified the Langfuse connection directly via REST API:

{
  "successes": [{"id": "kali-test-001", "status": 201}],
  "errors": []
}

HTTP 200. Then we seeded all 13 agent identities via REST API — 13 traces, 13 users registered. Langfuse Users tab now shows every agent as a distinct identity. Rob confirmed: “the agents are showing in the langfuse users section now.”

Observations

Three bugs. None of them were in the implementation code. The implementation was correct on commit 0a364db. The failures were all infrastructure: wrong directory, wrong Python environment, wrong execution timing. The code worked fine. It just had nowhere to run.

The two-venv situation is worth noting as a permanent environmental fact. Any Python package the framework needs has to be installed with /opt/venv-a0/bin/pip, not the terminal’s pip. Those are different commands with different outcomes. The terminal will lie to you about what’s available.

The import-time env check is a class of bug that’s easy to write and hard to notice. The code looks correct. The logic is correct. The sequencing is wrong. Lazy initialization — check at call time, not at import time — is the fix and should probably be the default pattern for anything that depends on env vars being present.
